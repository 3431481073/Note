## 一、项目自己学到的（【史】）

> **来源**：`history/DEVELOPMENT_LOG.md`。**这些是作者在 2026-09-10 ~ 09-18 的开发中记下的**，
> 本文件只是**摘录**，不改写。

| # | 结论 | 来源 |
| --- | --- | --- |
| 1 | **先修工具链再谈编译** —— rustup 半残时 `cargo` 可用、但一编译才炸；环境问题要前置排查。 | §2.1 + §7.1 |
| 2 | **依赖装在项目内，不污染全局环境。** | §2.2 |
| 3 | **首次 cargo 编译极长**（约 462 个 crate），这是这类项目的固有成本，不是出问题。 | §2.3 |
| 4 | **脚手架配置别照抄** —— `tsconfig` 引用、`vite.config` 谁检查要想清楚，删掉不需要的反而更稳。 | §3.1 + §7.2 |
| 5 | **能力开关要在 feature 层对上** —— `tauri.conf.json` 里开的 `assetProtocol`，`Cargo.toml` 不配 `protocol-asset` 会被 build script 拦截。 | §3.2 + §7.3 |
| 6 | 🔴 **时间戳排序必须单调且唯一** —— 毫秒并列会让「新建置顶」和游标分页随机出错。（**这就是 `summary.rs::now_ms()` 那个 CAS 的由来**） | §4.1 + §7.4 |
| 7 | **测试失败先分责任**：是「实现错」、「断言错」还是「测试数据不足」—— 用纸面推导状态机，别盲改实现。 | §4.2 + §4.3 + §7.5 |
| 8 | 🔴 **决定 dev/prod 的是 `custom-protocol` feature，不是 debug/release** —— 没开它，**即使 `--release` 也走 dev 模式去连 `localhost:1420`**。 | §8.3 + §10.1 |
| 9 | **同仓库里已有的正确范式要主动对齐** —— workbench 早就在用 `work_area()` 居中，便签却用了 `.center()`（而 tao 的 Windows 实现里没有它）。 | §19.7 |
| 10 | 🔴 **"一个 bug 反复修不好"时，先问一句"这其实是不是好几个 bug？"** —— 那十几小时实际拆出了 **6 个独立问题**，它们互相遮蔽，修好一个才暴露下一个。 | §19.9 |
| 11 | 🔴 **`SetWindowPos`（OS 窗口位置）和 CSS `transform`（webview 合成器）永远无法帧同步** —— 无论怎么串行、等动画、算补偿都补不回来。**正解是让参考系不变**（窗口固定宽、只用窗口内 CSS）。 | §19.6 |
| 12 | ⚠️ **合成器层的视觉伪影测不到** —— DOM/CSS/JS 层能全测，透明窗口+transform 的伪影**必须人眼看**。**这是"能从 CLI 测什么"的边界。** | §19.8（**作者自己标了"仍未闭环"**） |

## 二、整理这一站学到的（【站】）

> **来源**：本项目的第二十站（A–E 段 + 收尾段）。
> **这些都是"从外面看这个项目"才看得见的**，作者在写代码时不会记。

### 2.1 关于输出槽本身

| # | 结论 | 来源 |
| --- | --- | --- |
| 13 | 🔴 **这个输出槽是【从"本项目自己用"演进出来的】，不是按槽的标准设计的。** 它是**先存在、后被追认为槽** —— 所以带着内部实现的痕迹。 | C 段 C4 |
| 14 | 🔴 **`tags` 字段直接返回内部 `tags` 表的【主键】**，而**整个槽没有把 ID 换成名字的任何途径** —— 消费者拿到的是不可读的字符串，要读懂就必须知道生产者内部结构。 | B 段缺口一 |
| 15 | 🔴 **删除与恢复【不修改 `updated_at`】** —— 只比时间戳的消费者会**完全漏掉**这两类事件。判断删除只能看 `deleted_at` 字段。 | B 段边界一 |
| 16 | 🔴 **`purge` 是物理 `DELETE`，没有墓碑** —— 彻底删除后该 id **从清单里整个消失**，消费者只能靠"上次有、这次没有"推断。 | B 段边界二 |
| 17 | 🔴 **这是一个"活槽"：没有文件、没有 mtime、没有标记文件** —— 消费者要判断"有没有变化"，**只能全量拉一遍然后自己 diff**。 | B 段边界三 + 收尾段实测 |

### 2.2 关于文档与事实

| # | 结论 | 来源 |
| --- | --- | --- |
| 18 | 🔴 **"加证据"这件事，第一次做就抓出 5 处不实**（原文错 3 + 我自己错 2）—— **它不是形式主义**。 | D 段 |
| 19 | 🔴 **只做「文档→实物」是不够的，必须做「实物→文档」** —— 前者防**编造**，后者防**漏记**，**两者抓的东西完全不重叠**。**实测：26 个 Tauri 命令有 15 个、3 条事件有 2 条、4 张表的字段结构，都没被登记过。** | 收尾段 |
| 20 | 🔴 **「日志里有」≠「文档里有」** —— 4 张表的清单其实写在 `log.md` 里，**但日志按日期堆积，没人会去那里查表结构**。 | 收尾段 |
| 21 | 🔴 **「已知错留在文档里，比没写更坏」** —— 留错会让人当真，漏写至少不误导。 | E 段拍板 |
| 22 | **在 `docs\` 内部再分层，会造成断链** —— C2 搬 6 个文件，`docs\` 里产生了 **28 处**指向旧位置的引用（6 条链接直接 404）。 | C 段 |
| 23 | **`log.md` 里的路径是【写入时刻】的快照，会与现状相反** —— 它们**不该改**（改了就是篡改历史），只能在顶部声明。 | C 段 + D 段 |

### 2.3 关于我自己（Claude）—— 这一站暴露的

## 五、2026-10-09 补记（第二十一站 · 窗口行为整改站）

> **来源**：本项目的第二十一站。它**与前几站不同 —— 这一站改了代码**（见 [log.md](log.md)）。
> **这一节的结论，多数是"我（Claude）在这一站暴露的"，不是项目本身的。**

| # | 结论 | 来源 |
| --- | --- | --- |
| 29 | 🔴 **"一个小需求被扩写成一个大改造" —— 这是 #10 的反面教材。** 用户要的只是"**别总在最顶层**"，实际却改出了一整套几何追踪机制（rAF 节流 + 结果去重 + `transitionend/animationend` 捕获 + `ResizeObserver` + 对整个 `document.body` 的 `MutationObserver`）。**用户反馈"你改完之后它非常不稳定"，全部拆除。** | 站21 §七 |
| 30 | 🔴 **一个需求只做一件事。** 拆除后 `App.tsx` 的改动量从 **107 行降到 10 行** —— **多出来的 97 行，没有一行是用户要的。** | 站21 §七 |
| 31 | 🔴 **先读项目自己的"已知限制"清单，能省掉一整轮排查。** 「透明窗口合成器伪影」**早在 `README.md:73` / `DEVELOPMENT_LOG.md` §19.8 就被标为"仍未闭环"** —— 而我在读到它之前，**已经推翻了九个假设。** | 站21 §六 · [run.md](run.md) 第十二节 |
| 32 | ✅ **"先测量、后修改"是对的。** `WM_NCHITTEST` 探针（直接问窗口「这个点你收不收」）+ `trace.log`，让九个假设**各自拿到反证**，而不是"觉得不像"。**测量工具一旦建好，取证成本趋近于零。** | 站21 §六 · [runtime-log.md](runtime-log.md) |
| 33 | 🔴 **"用户以为关了，其实没关" 是一个独立的危险类别。** 点 × 只 `hide()`，进程**常驻了 5 天** —— 桌面软件里**"关闭"必须是真关闭**，否则用户对状态的每一次推断都是错的（包括他自己写的脚本）。 | 站21 §三 · [service.md](service.md) 第十一节 |
| 34 | 🔴 **改代码会【静默】让文档的 `file:line` 引用失效。** 本轮只新增两条命令，就让 **4 个文件**的行号发生了位移。**#19 那套"加证据"的机制缺一条：改动之后要标漂移。** | 站21 §五 |
| 35 | ⚠️ **我跨系统判断错了一次，代价是白杀用户正在用的窗口几次**：把"反复被拉起的便签进程"归因于 `service-manager` 的守护进程；**读它的 `config/projects/*.yaml` 后当场收回**（它托管的是 catcher/infra/proxy_pool，与本项目无关）。**跨系统的因果推断，先读对方的配置。** | 站21 §七 |
| 36 | ⚠️ **"每次启动多一张空白便签"的根因是【静默吞错】。** `init()` 里 `loadFirstPage` 失败被 `catch` 掉，随后把"看起来是空的"当成"空库"→ **自动新建**。**吞错之后紧接着做有副作用的判断，是数据污染的经典配方。** | 站21 §二 |

### 一句话

> 🔴 **这一站最值得学的，不是任何一个 bug，是那条 #10 的镜像**：
> **#10 说"一个 bug 反复修不好时，先问它是不是好几个 bug"；**
> **这一站说"一个小需求做不完时，先问自己是不是在做别的东西"。**
