## 3. 技术选型决定（我拍板，附理由）

| 项 | 决定 | 理由 |
| --- | --- | --- |
| 标签/项目存储 | `pages.tags` / `pages.projects` 为 **JSON 数组列** | 个人量级小，读写整字段最快；不拆 join 表避免多余索引与迁移复杂度 |
| outline 树存储 | `pages.nodes_json` 单列存整棵树 JSON | 树只在视图模式整体读改写，单列最简单、迁移成本最低；量大再拆 `nodes` 表 |
| 标签/项目过滤 | **放后端 SQL**（`json_each` / `EXISTS`） | 与游标分页一起才能不漏页；前端过滤会只滤已加载页 |
| 搜索 | 后端 `LIKE` 匹配 `title` 与 `content`，`ESCAPE '\'` | 沿用现有转义，扩展字段即可 |
| 摘要 | 定 20 字；标题独立字段，正文缩略不含标题 | 满足“20 够用 + 有标题时扫掉标题” |
| 事件 | 扩 `ChangedPayload`（`title/kind/tags/projects` 均 `Option`），仍 `op` 枚举 | 前端 `applyChangedPayload` 幂等合并继续成立 |
| 迁移 | `schema_migrations(version, applied_at)` 记录，逐版本 `ALTER` | 旧库无损升级，可复跑/可回退 |
| 树坐标 | 写库前 clamp 到画布范围 | 防脏数据越界 |

## 5. 我的疑问（都是你“能感知的界面”，非后台细节；不回就按默认做）

**Q1 · 多视图之间怎么切换？**
你的定稿里“视图模式加号=新建视图”，意味着可能有多条视图；但没说在视图模式下怎么在多个视图间切换。
- 我的默认：视图模式**中间的卡片列用于列出所有“视图”**（一条视图一张卡，点选切换当前视图，左侧树随之切换），与 v12 三栏布局一致。
- 请确认：是否按“中间列列视图、点选切换”？还是第一版先只支持一条视图？

**Q2 · 窗口加宽的具体数值？**
- 我的默认：**卡片模式保持 740×648**；**视图模式加宽到 1300×648**（宽按 v12 三栏 550+226+400 + 间隙 + 左右边距 ≈ 1300，高不变 648），动态 `set_size` 后重新居中、保持置顶。
- 请确认这个数值是否可接受，或给出你想要的宽/高。

**Q3 · “标签/项目只在详情界面出现”的口径**
我理解为：**卡片列表不显示标签行/标题行**（已照做）；但**搜索框聚焦展开的过滤器里仍保留标签/项目下拉**用于筛选（因为 §1 定了“搜索叠加标签 AND/项目 OR 过滤”）。
- 我的默认：搜索过滤器保留标签/项目下拉。若你本意是“连搜索过滤器也不要标签/项目”，请指出（那样标签/项目就只剩详情界面能设、不能筛）。

**Q4 · 节点导入卡片时“询问是否添加标题”的具体形态**
- 我的默认：点「＋卡片」弹一个**标题输入框（可留空）**，留空=不带标题，确定后生成带「视图：xxx」标签的便签；重复导入=撤销。
- 请确认是“输入框可留空”还是“是/否二选一”。

> 除以上 4 点外，其余后台细节（字段、SQL、事件拆分、resize 实现、单测、树坐标 clamp 等）我按 §3 自行拍板，不再反复问。

## 7. 风险与依赖

1. **阶段 1 迁移是地基**：加列/版本号/旧库无损必须先行并锁定，后续阶段都建立在它上面。
2. **事件幂等合并**：新增字段后 `applyChangedPayload` 若不对齐，会重演“同 id 重复插入→多聚焦卡顿”，阶段 3/4 必须回归验证。
3. **折叠动画 + 动态 resize 组合**：动画期间 resize 可能抖动，阶段 5 需用“动画锁 + 一次性 set_size”规避。
4. **树坐标脏数据**：写库前 clamp，防越界。
5. **排序不切 `updated_at`**：阶段 2 只做搜索/过滤，不碰排序相关索引与游标，避免误伤基线。
